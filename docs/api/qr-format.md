# QR code formats

Two distinct QR payloads exist in the Event Tickets ecosystem. The app must parse both.
(Facts verified against Event Tickets 5.29.x source — `TEC\Tickets\QR\Connector` in the
free plugin; QR support moved from Event Tickets Plus into free Event Tickets at 5.7.0.)

## 1. Ticket QR (on the attendee's emailed/printed ticket) — what the door scanner reads

A plain **URL** (not JSON): the site's home URL plus query args:

| Query arg | Meaning |
|---|---|
| `event_qr_code` | Constant marker (`1`) identifying this as a ticket QR |
| `ticket_id` | ⚠️ **The attendee post ID** (misleading name — it is NOT the ticket product ID) |
| `event_id` | WordPress post ID of the event |
| `security_code` | The attendee's per-provider security code (8 chars); must match `Attendee.security_code` |
| `path` | URL-encoded REST route of the site's built-in QR endpoint (`/wp-json/tribe/tickets/v1/qr`) — ignore; we use the companion API |

**Parsing rules for `App\Services\QrParser`:**

1. Must be a parseable absolute URL with query args containing at least `ticket_id`,
   `event_id`, and `security_code` (treat `event_qr_code` as optional belt-and-braces).
2. Extract `{attendee_id: (int) ticket_id, event_id: (int) event_id, security_code: (string)}`.
3. Tolerate URL-encoding variants and extra/reordered query args. Host does not need to
   match the connected site (organizers may scan while connected via a different hostname
   than the ticket was issued under) — validation is by attendee ID + security code lookup.
4. Anything else (random URLs, vCards, wifi QRs, the JSON pairing QR) → `not a ticket` result,
   which the scan screen surfaces as RED "Not a ticket QR".

https://example.test/?event_qr_code=1&ticket_id=9004&event_id=501&security_code=8466b17a&path=%2Fwp-json%2Ftribe%2Ftickets%2Fv1%2Fqr

|---|---|---|
| 9001 (Ada Lovelace, GA, completed, not checked in) | GREEN — then AMBER on rescan |

## 2. Companion-plugin pairing QR (wp-admin → Tickets → Scanner App) — PREFERRED

**JSON**, generated by our `event-ticket-scanner-companion` plugin's admin page:

```json
{"v": 1, "type": "event-ticket-scanner-pair", "url": "https://wp-dev.test", "user": "doorstaff", "token": "317bb01021b1b1114dcaf1f8e59fec88269e9bf5"}
```

Flow: the app scans this, then POSTs `{token, device_name}` to `{url}/wp-json/event-ticket-scanner/v1/pair`
(see `openapi.yaml` → `/pair`). The token is **single-use and expires in 5 minutes**; the
response contains `{site_url, username, app_password}` which the app stores (password in
SecureStorage only) and thereafter uses as normal Basic auth. The QR never contains a
long-lived credential.

Parsing rule: valid JSON with `type == "event-ticket-scanner-pair"` and `url` + `token` keys →
run the pair exchange. On 403 (expired/used token) prompt the organizer to generate a
fresh code in wp-admin.

## 3. Legacy ET+ app-pairing QR (wp-admin → Tickets → Settings → Integrations)

**JSON**, used by the official ET+ app to pair a site:

```json
{"url": "https://example.test", "api_key": "1a2b3c4d", "tec": true}
```

Our app **only uses `url`** to prefill the site URL on the Connect Site screen — we
authenticate with WordPress Application Passwords, never with the 8-char shared `api_key`
(it is a weak site-wide secret; see PLAN.md security notes). Parsing rule: valid JSON with
a `url` key (and no `type`/`token`) → treat as legacy pairing QR; prefill and prompt for
username + application password.
